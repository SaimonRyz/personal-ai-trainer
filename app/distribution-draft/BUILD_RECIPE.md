# Проверяемый рецепт сборки на компьютере будущего пользователя

Статус: экспериментальная альфа; успешное развёртывание подтверждено владельцем. Каждый новый компьютер проверяется отдельно. Поддерживаемая платформа — Mac с Apple Silicon, Docker linux/arm64, CPython 3.12.14.

## Источники

- Точные внешние Docker references и официальные страницы metadata: [RELEASE_INPUTS.json](RELEASE_INPUTS.json). Три входа — `python:3.12.14-slim-bookworm`, `uv:0.12.5-alpine3.22`, `postgres:17.11-bookworm`, каждый с полным registry digest. Тег рядом с digest нужен для понятности, но выбирается digest.
- Python runtime: `uv.lock`; у всех 55 внешних пакетов источник `https://pypi.org/simple`, URL архивов на `https://files.pythonhosted.org`, их размеры и SHA-256 в lock. Не использовать зеркала, дополнительный index, `latest` или произвольный wheel.
- Изолированная сборка локального проекта: шесть точных версий и SHA-256 в [build-constraints.txt](build-constraints.txt). Для трёх build-зависимостей, отсутствующих в lock, официальные wheel URL, размеры и SHA-256 закреплены в [BUILD_ARTIFACTS.json](BUILD_ARTIFACTS.json). [plan_release_inputs.py](plan_release_inputs.py) вычисляет полный список wheel для macOS ARM64 и Linux ARM64 без загрузок. Runtime- и build-пакеты устанавливаются из проверенного Linux wheelhouse без сети во время сборки.
- Исходный код: только проверенная release-ревизия. Порядок определения источника — в `../../SOURCE_VERIFICATION.md`; отдельный SHA из чата не требуется.

## Последовательность после согласия пользователя целевого компьютера

1. Установочный агент проверяет платформу, инструменты и локальный Docker context. Упаковщик заранее включает `RELEASE_WHEEL_PLAN.json` в манифест пакета: Codex может прочитать полный список входов и на машине без Python 3.12. При наличии системного Python 3.9+ `preflight_release.py` одним read-only вызовом сверяет внутреннюю целостность пакета, версии инструментов и точные отсутствующие wheel/образы; без внешнего SHA-256 manifest результат `SELF_CONSISTENT_ONLY` означает внутреннюю целостность и при согласованном источнике не блокирует установку. При наличии CPython 3.12 агент выполняет `python3.12 distribution-draft/verify_release_inputs.py`, `python3.12 distribution-draft/plan_release_inputs.py` и `python3.12 distribution-draft/prepare_release_wheels.py` **без `--execute`**. Требуются `RELEASE_INPUTS_STATIC_PASS` с `runtime=NOT_CHECKED` и `PLAN_ONLY_NOT_DOWNLOADED`; последняя команда показывает отсутствие уже имеющихся wheel и суммарный объём без записи или загрузки. После установки отсутствующего CPython эти проверки обязательны до wheel-загрузок. Любая ошибка блокирует сборку.
2. Агент заранее показывает пользователю один полный список входящих загрузок и изменений из плана. После разрешения получает **только** три Docker references из `RELEASE_INPUTS.json` по полным digest для `linux/arm64`. Для точных Python wheel из `uv.lock`/`BUILD_ARTIFACTS.json` запускает `python3.12 distribution-draft/prepare_release_wheels.py --execute`: команда повторно сверяет уже имеющиеся файлы, запрещает redirect и подмену URL, проверяет каждый размер и SHA-256 перед публикацией. Linux wheel помещаются в локальный `wheelhouse/linux-arm64`, host wheel — в `wheelhouse/macos-arm64`; оба набора содержат также шесть build-зависимостей и точный `runtime-requirements.txt`. Оба каталога игнорируются Git и исключены из исходного архива. Установщики и Docker exports автора в проект не копируются.
   Если Docker Desktop отсутствует, путь его установки — проверенный официальный `.dmg` и интерактивная процедура [Docker для Mac](https://docs.docker.com/desktop/setup/install/mac-install/): пользователь выполняет перенос в Applications, принятие условий и системные диалоги; агент после этого проверяет результат. Командная установка из официального руководства требует `sudo` и в этой процедуре запрещена. Установка Docker не начинается, пока точный артефакт и его общий объём не входят в согласованный пакет.
3. После получения проверяет каждый downloaded artifact по закреплённому SHA-256/registry digest, размеру (где указан), платформе и источнику. Проверяет, что Docker context локален, а для `uv` не подменён index. Host `.venv` создаёт из CPython 3.12.14, затем ставит runtime wheel через `uv pip install --python .venv/bin/python --offline --no-index --find-links wheelhouse/macos-arm64 --require-hashes --no-build -r wheelhouse/macos-arm64/runtime-requirements.txt`, build wheel аналогично через `-r distribution-draft/build-constraints.txt`, а локальный проект — через `uv pip install --python .venv/bin/python --offline --no-build-isolation --no-deps .`. Если source metadata не подтверждает pin, останавливается без замены версии.
4. `build_release.py` до обращения к Docker требует полный точный Linux wheelhouse, проверяет размер и SHA-256 каждого wheel и запрещает лишние файлы. Затем собирает `Dockerfile.release` с `--platform=linux/arm64`, `--pull=false` и `--network=none`. Dockerfile ставит зависимости из wheelhouse с `--offline --no-index --require-hashes`; `.env`, база и пользовательские файлы исключены из build context. Фактическую работоспособность доказывает только runtime gate.
5. Проверяет в полученном image версию Python, платформу, установленный перечень пакетов, импорт `trainer` и `trainer_mcp`, SHA-256 `uv.lock` и соответствие source fingerprint. Записывает полный image ID и результаты в локальное доказательство сборки, не в Git и не в сеть.
6. PostgreSQL image сверяет отдельно с полным ожидаемым ID из `RELEASE_INPUTS.json`. Создание `.env`, volume и тестовой БД — отдельный owner gate; build PASS сам по себе не разрешает запуск или миграцию.

Запись `RELEASE_INPUTS_STATIC_PASS` подтверждает **только согласованность текста, JSON, Dockerfile, constraints и текущего lock**. Для `BUILD_PASS` нужны фактическая чистая сборка и проверка image. Для `INSTALL_PASS` дополнительно нужны чистая host-установка и тестовый runtime. Для пользовательского `READY` — проверки API/MCP и обнаружения инструментов в новом чате. Эти статусы не подменяют друг друга.
