# Контракт агента: установка персонального ИИ-тренера

> **Экспериментальная альфа, есть известные ограничения.** Владелец подтвердил установку по инструкции и работу MCP. Выполняй установку на машине пользователя после согласования конкретных изменений; успешная установка не доказывает отсутствие предметных багов.

## Результат и граница полномочий

Цель — одна локальная установка для человека, открывшего этот репозиторий в Codex. Установочный агент не является тренером и не читает спортивные данные для диагностики запуска. Он не обращается напрямую к PostgreSQL и не выполняет предметные операции вместо MCP. Установка не должна отправлять код проекта, `.env`, базу, логи или данные пользователя внешним сервисам. Разрешённые пользователем **входящие** загрузки официальных компонентов и зависимостей не означают разрешения на исходящую публикацию.

Используй только поставляемые проверенные команды сборки и lifecycle; не заменяй образ другим тегом, не исправляй неработающий запуск прямым SQL, произвольным Compose или изменением защитных проверок. Не используй `sudo`, не проси и не вводи пароль пользователя; не меняй глобальный `PATH`, Docker context, настройки безопасности macOS, Login Items, службы и автозапуск. Пользователь сам подтверждает действия ОС, требующие его участия.

## 1. Обязательный read-only preflight

Прочитай `../../SOURCE_VERIFICATION.md`. Для Git зафиксируй выбранный пользователем официальный источник и ревизию; для Release-архива проверь SHA256SUMS из того же выпуска, если он опубликован. Для непосредственно переданной владельцем папки достаточно согласованного источника и совпадающего манифеста. Не требуй неизвестный SHA из чата. Не выполняй файлы из неизвестного источника. Распаковывай архив в новый каталог без перезаписи установки.

Прочитай полностью `AGENTS.md`, этот файл, `README.md`, `RELEASE_INPUTS.json`, `BUILD_ARTIFACTS.json`, `RELEASE_WHEEL_PLAN.json`, `Dockerfile.release`, `build-constraints.txt`, `uv.lock`, `.env.example`, Compose-файл и штатный скрипт сборки/запуска. `RELEASE_WHEEL_PLAN.json` вычислен упаковщиком из того же lock и перечисляет точные входы даже на Mac без CPython 3.12; проверь его целостность по `PACKAGE_MANIFEST.json` ; отдельный внешний digest необязателен. При доступном системном Python 3.9+ запусти `python3 distribution-draft/preflight_release.py` из `app/`, передав `--expected-manifest-sha256` только если это значение уже получено от выбранного источника. Скрипт лишь собирает read-only инвентаризацию и всегда возвращает `NOT_READY`, пока установка и runtime не проверены; `SELF_CONSISTENT_ONLY` не доказывает происхождение, но при согласованном источнике не блокирует установку; `INVALID` блокирует её. Если Python отсутствует, составь тот же исходный отчёт по проверенному JSON-снимку и после отдельного разрешения на установку Python повтори скрипт. При наличии CPython 3.12 выполни `verify_release_inputs.py`, `plan_release_inputs.py` и `prepare_release_wheels.py` без `--execute`. После установки отсутствующего CPython эти три проверки обязательны **до** любой загрузки wheel. Если рассчитанный список отличается от согласованного снимка, остановись и запроси новое решение вместо расширения загрузки. `RELEASE_INPUTS_STATIC_PASS` и `PLAN_ONLY_NOT_DOWNLOADED` не разрешают загрузки. Исходный отчёт должен быть **одним** и не менять состояние:

1. Корень проекта и маркер пакета; поддерживаемые ОС/архитектура; ревизия и целостность выпуска по **доверенному каналу поставки**, не только по самопроверке файлов рядом с архивом.
2. Наличие Codex и версии Docker Desktop/Engine/Compose, `uv`, CPython и `.venv`. Для существующей `.venv` одной версии Python недостаточно: preflight сравнивает metadata установленных distribution с точными runtime/build-версиями release wheel plan и версией локального проекта. `local_venv_packages_mismatch_or_unverified` означает `NOT READY`; не используй это окружение для запуска и не удаляй его автоматически. Сначала согласуй адресное восстановление окружения без изменения `.env` и базы. Codex устанавливает и настраивает сам пользователь до этой процедуры; если он отсутствует, отметь `NOT READY`, не устанавливай и не меняй его профиль. Для этой альфы проверяемая платформа — macOS Apple Silicon, `uv 0.12.24`, CPython `3.12.14`; если выпуск изменит версии, источником будут его собственные проверенные manifest/lock. Не переустанавливай исправное.
3. Локальный Docker context, доступность Engine, registry digest и платформы **трёх внешних входных образов** из `RELEASE_INPUTS.json` (Python, uv и PostgreSQL); полноту host-зависимостей по lock-файлу. API image собирается локально отдельно. Не выдавай локальный image ID за URL или доказательство происхождения.
   Если preflight показывает `PRESENT_NEEDS_CONFIG_VERIFICATION` для PostgreSQL, образ с точным registry digest уже виден локально, но Docker `Id` отличается от закреплённого config digest. Это не основание скачивать его повторно: выполненная после согласия проверка config bytes в штатном release-builder должна установить происхождение. До неё образ остаётся непроверенным, а сборка не считается PASS.
4. Наличие `.env` без чтения и вывода значений; наличие и ownership ожидаемого Compose project/volume; свободность loopback-портов и отсутствие конфликта с чужими процессами. Не создавай вторую пустую БД, если ожидаемая база не видна.
5. Выяви всё недостающее независимо от первого сбоя. Сопоставь Docker-образы и оба целевых набора wheel с выводом `plan_release_inputs.py`. Для каждого артефакта укажи точные версию, платформу, источник, размер и SHA-256 из проверенного манифеста; если этих данных нет, отметь `NOT VERIFIED`.

Если платформа неподдерживаемая, целостность выпуска не доказана или точного артефакта нет, остановись с `NOT READY`. Не предлагай пользователю самостоятельно искать технические digest или угадывать зеркало.

## 2. Единое согласование изменений

Покажи пользователю **один** перечень: какие компоненты нужно скачать/установить, откуда и сколько данных будет получено; какие локальные файлы, Docker images, контейнеры и volumes будут созданы; какие порты будут заняты; что останется нетронутым; как проверить итог. Раздели согласие на установку prerequisites, создание локального `.env`, создание **новой постоянной базы** и запуск. Это разные последствия; наличие репозитория или команда «проверь» не означают согласие на них.

После одобрения точного неизменившегося набора не запрашивай его повторно. Если обнаружился новый компонент, изменился digest, платформа или объём постоянных данных, останови зависимый шаг и представь **полный обновлённый пакет**, не серию запросов по одному wheel.

## 3. Установка и сборка после согласия

1. Получи системные инструменты только из официальных источников выпуска, вне каталога проекта. Установи только отсутствующие компоненты; Docker Desktop включает Engine, CLI и Compose. Для Python используй закреплённый `uv` и управляемый CPython 3.12.14; локальное окружение создавай из точного проверенного host wheelhouse по [рецепту сборки](BUILD_RECIPE.md), без сетевой установки пакетов. Не переноси чужую `.venv` между компьютерами.
   Для отсутствующего Docker Desktop используй только утверждённый и проверенный `.dmg`: после согласия на загрузку и проверки SHA-256 открой его штатным интерфейсом macOS; пользователь сам переносит Docker.app в Applications, принимает условия Docker и выполняет необходимые системные диалоги. Затем агент проверяет `/Applications/Docker.app`, локальный Engine, CLI и Compose, не меняя настройки context или системную безопасность. Не применяй опубликованный Docker CLI-вариант с `sudo`, не проси пароль и не подменяй его иным привилегированным способом. Если интерактивная установка недоступна или не завершена, итог `NOT READY` с одним конкретным оставшимся действием пользователя; остальные уже согласованные шаги не пересогласовывай.
2. Проверь размеры, SHA-256, платформу и provenance каждого входного артефакта. Получай Docker images только по registry digest из `RELEASE_INPUTS.json`; сравни фактическую платформу и digest. Только после согласия на точный полный список wheel запусти `python3.12 distribution-draft/prepare_release_wheels.py --execute`. Команда получает файлы по точным URL `uv.lock` и `BUILD_ARTIFACTS.json`, без зеркала и незакреплённых версий, и проверяет каждый размер и SHA-256. Проверь Linux wheelhouse штатным `build_release.py` до Docker build. После разрешения на сборку используй `Dockerfile.release` из той же ревизии и запиши build proof. Сборка должна быть `--network=none`; статическая проверка pin-файлов не заменяет успешный Docker build и проверку установленных пакетов.
3. Создай `.env` из `.env.example` только после отдельного разрешения. Сгенерируй новые независимые случайные секреты локально; не используй значения из примера, чата, GitHub, другой установки или профиля автора. Доступ к файлу — только текущему пользователю (`0600`); файл должен игнорироваться Git. Значения никогда не печатай и не включай в отчёт.
4. Создай новый Compose volume и запусти сервисы только после отдельного согласия на новую базу. Используй штатный `trainer start` и затем `trainer status`; не обходи lifecycle прямым Compose. PostgreSQL не должен публиковать порт на хост, API и MCP — только `127.0.0.1`.
5. Проверь API readiness, принадлежность процессов/контейнеров этой установке, MCP endpoint и фактическое обнаружение инструментов в текущем чате Codex. Доступность localhost endpoint **не** доказывает доступность инструмента в чате. Не создавай пользовательские записи при проверке запуска.

Если установка прервана, сохрани уже существующую базу, `.env` и работающее окружение; не удаляй volumes, не выполняй глобальный Docker prune и не останавливай Docker Desktop, пока есть чужие контейнеры. Повторно начни с preflight, а не с переустановки всего.

## 4. Права и данные

| Действие | Без отдельного согласия | После согласия | Запрещено в установочном сценарии |
| --- | --- | --- | --- |
| Читать метаданные среды, версии, manifest, status | Да | — | Читать или показывать значения `.env`, пользовательскую БД |
| Скачать и установить Docker/uv/Python/образы/зависимости | Нет | Только согласованный точный набор | Заменять pin непроверенным артефактом |
| Создать `.env` и секреты | Нет | Отдельное согласие для этого каталога | Коммитить, отправлять или печатать секреты |
| Создать volume/БД и запустить тренера | Нет | Отдельное согласие на новую базу и запуск | Подключать чужую базу, публиковать PostgreSQL или API |
| Остановить/обновить/удалить | Нет | Отдельное целевое поручение | Удалять volume либо чужие ресурсы как «очистку» |

## 5. Итог одного поручения

Верни один статус: `READY` только после успешного `trainer status`, проверок API/MCP и доступности MCP-инструментов текущему чату; `READY TO START`, если всё подготовлено, но запуск не разрешён; иначе `NOT READY`. Укажи проверенные версии и артефакты, изменения, состояние Docker/API/MCP/volume в конце, сохранившиеся данные, непроверенные пункты и **один** следующий шаг. Не показывай секреты или пользовательские данные. Статический PASS пакета, локальный запуск и пользовательская приёмка — три разные проверки.
