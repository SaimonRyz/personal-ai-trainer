# Воспроизводимые образы и зависимости: входы и текущий статус

> **Экспериментальная альфа.** Установка и MCP подтверждены владельцем. Ниже сохранены точные источники и исторические результаты проверки входов; они не являются запретом установки.

## Цепочка сборки на поддерживаемой платформе

Целевая платформа текущего кандидата — macOS Apple Silicon; Docker images имеют платформу `linux/arm64`. Источник Python-сервиса, MCP и миграций один: проверенная ревизия будущего release-репозитория. `pyproject.toml` определяет прямые зависимости, `uv.lock` — их точные разрешённые версии и архивы. Хостовые зависимости для lifecycle/MCP устанавливаются в новую `.venv`; API image строится из **той же** ревизии исходников. Runtime PostgreSQL image — отдельный вход, не часть API image. Docker Desktop/Compose, `uv`, CPython и Codex не хранятся в Git-репозитории приложения.

Для будущего выпуска подготовлены [закреплённые входы](RELEASE_INPUTS.json), [Dockerfile-кандидат](Dockerfile.release), [build-constraints с SHA-256](build-constraints.txt) и [read-only статическая проверка](verify_release_inputs.py). Проверка запускается из корня проекта командой `python3.12 distribution-draft/verify_release_inputs.py`; она сверяет digest образов, SHA-256 `uv.lock`, происхождение и хеши 264 артефактов 55 внешних пакетов, шесть build-зависимостей и обязательные команды Dockerfile. Её результат `RELEASE_INPUTS_STATIC_PASS ... runtime=NOT_CHECKED` **не** доказывает, что Docker build, host install или приложение работают на чистом компьютере.

Действующий исходный Dockerfile разработки (`Dockerfile`) использует незакреплённые digest теги `python:3.12.14-slim-bookworm` и `ghcr.io/astral-sh/uv:0.12.5`; **не использовать его как публичный рецепт**. Частная альфа зависит от локального image ID, который нельзя получить из публичного реестра по одному этому ID. В отдельном `Dockerfile.release` базовые образы закреплены registry digest; runtime- и build-пакеты устанавливаются из проверенного Linux wheelhouse через `uv pip install --offline --no-index --require-hashes --no-build`, локальный проект — без новых зависимостей. Полный план wheel вычисляется `plan_release_inputs.py` по `uv.lock` и `BUILD_ARTIFACTS.json`. Успешное развёртывание подтверждено владельцем; build proof каждой новой установки формируется локально.

Для PostgreSQL в частном переносимом кандидате закреплён официальный `postgres:17.11-bookworm`, `linux/arm64/v8`, platform manifest digest `sha256:f97ca6038b7641359fef23126949d824ac68edd8a7081b424d6a78e1f7076f8e`, ожидаемый config/image ID `sha256:8942ba4a60918c2b98bcad5c842453a765898854a9fec87f64ec816bf44559be`. Эти значения ещё не подтверждены локальным pull/import для текущей публичной редакции. Тег без проверки digest и image ID недостаточен.

Размер Docker Desktop получен из HTTP HEAD 28.10.2026; размеры и SHA-256 uv/CPython дополнительно сверены с GitHub release asset metadata. Это не проверка фактических файлов после скачивания. ## Историческая инвентаризация до успешного пользовательского развёртывания

| Вход | Имеется | Не доказано / требуется |
| --- | --- | --- |
| `pyproject.toml`, `uv.lock` | Файлы разработки и закреплённый lock; совпадение lock внутри локального dependency image проверялось | Публичный release snapshot и новый полный build-proof от чистых входов |
| Host-зависимости macOS ARM64 | `uv.lock` содержит версии и hash-значения артефактов | На новом компьютере агент должен после согласия пользователя получить совместимые файлы из закреплённых источников и проверить lock. Частный wheelhouse автора не является частью публичного репозитория; clean install по сети пока не проходил |
| Dependency image API | Локальный image и его `docker save` archive существуют | Независимая аттестация upstream-слоёв и воспроизводимая сборка из опубликованных закреплённых входов; чистая сборка ранее остановилась на отсутствии `psycopg==3.3.4` в Linux build cache |
| PostgreSQL image | Утверждён точный platform digest | Точный образ отсутствовал при последней проверке; pull, проверка ID, экспорт/импорт и чистый runtime-gate не проходили |
| API image | Overlay-сборка из текущего source archive поверх локального dependency image дала `ALPHA_IMAGE_STATIC_PASS` | Сборка из будущего release snapshot на чистом компьютере и пользовательский запуск |

## Требуемый проверяемый процесс подготовки выпуска

1. Зафиксировать поддерживаемую платформу, release revision, SHA-256 `pyproject.toml` и `uv.lock`, версии сборочных инструментов и **registry digest** входных Python/uv/PostgreSQL images. Кандидат registry pins находится в `RELEASE_INPUTS.json`; у нового выпуска его повторно сверить с официальными источниками. Не брать `latest`; не считать локальный image ID заменой registry digest.
2. Использовать `uv.lock` как источник версий, PyPI registry и URL/размеров/SHA-256 Python-артефактов. Для сборочной изоляции использовать `build-constraints.txt` и не разрешать непроверенные build-версии. На целевой платформе дополнительно проверить, что все выбранные wheel совместимы с CPython 3.12 и macOS ARM64 либо `linux/arm64`. **Файлы wheel не требуется заранее скачивать на компьютер автора или помещать в Git.**
3. На чистом целевом компьютере агент сначала составляет один полный перечень необходимых входящих загрузок, получает согласие пользователя, затем скачивает и проверяет их там. Выполняет host sync с точными `uv` и CPython без прежнего cache; отдельно собирает `Dockerfile.release` из pinned base images и закреплённых Python/build-зависимостей. Проверяет `uv.lock` и platform metadata внутри образа. При новом недостающем артефакте — `NOT READY` и обновлённый полный перечень, без выбора похожей версии.
4. Проверить импорт API/MCP, fingerprint исходников, полный image ID и `linux/arm64`; результат записать в build proof. PostgreSQL image получить только по pinned platform digest и сверить config/image ID. Повторить сборку из той же ревизии, сравнить входные digest и результат. Совпадение входов не гарантирует побайтового равенства output image, поэтому различие output ID объяснить или заблокировать выпуск.
5. Проверить весь маршрут на чистом поддерживаемом компьютере: получение/проверка артефактов, хостовые зависимости, Docker images, API build, отдельная тестовая БД, API/MCP readiness и обнаружение инструментов Codex. Записать фактические версии и хеши в release manifest. Только после этого инструкция может обещать воспроизводимую установку.

Переносимый офлайн-набор для второго Mac и публичная поставка — разные цели. Частный `docker save` archive и локальный пакет согласования загрузок автора **не являются входами** этого сценария. Будущий пользователь получает исходники через разрешённый ему канал, а агент на **его** компьютере готовит и проверяет нужные зависимости по закреплённому рецепту. Никакой этап выше не разрешает автоматически отправлять исходники или данные проекта в сеть.
